## Про «свой Auth = месяцы»

Перегиб. Не «полгода», а **отдельный мини-эпик ~1–3 недели**, если резать этапы:

1. Postgres + users/sessions на VPS  
2. email+password (+ позже OAuth)  
3. перенос профилей / `finish_game` / рейтинга  

Supabase Auth+таблицы мы собрали быстро, потому что **готовая платформа**. Своё — тоже реально, просто **не бесплатно по вниманию**.

**Минусы своей авторизации «вместо» Supabase сейчас:** вы тащите сброс пароля, OAuth Google, сессии, анти-брут, RLS/политики, миграции users — и параллельно переписываете рейтинг/архив/профили. Пока идёт прод-закал WS, это конкурирует с важнее.

**Нормальный путь:** сейчас WS принимает **JWT Supabase** (`WS_AUTH=required`). Своя СА — позже как замена или dual-issuer, без блокировки публичного `wss://`.

Когда дойдём — можно и рейтинг/сезоны/турнирные лестницы сделать «по-взрослому» на своём бэке. До тех пор Supabase = identity + persistent data.

## Актуальный порядок работ

### Волна 0 — Production WS (честный стол)

Цель: portable игровой сервер, на котором позже можно держать платящих. Друг/облако/свой Linux — один контракт. **Пакет хосту не отдаём, пока затвор не зелёный.**

1. JWT fail-closed (`WS_AUTH=required`), проекция рук, членская подписка.
2. Конец партии и Elo пишет WS (`finish_game_from_server`), не клиент.
3. Артефакт `server/dist` + `/etc/updown/ws.env` + `/api/ready`. См. [PRODUCTION-WS.md](./PRODUCTION-WS.md).
4. Цепочка конец партии → матч/Elo на staging.
5. Мобильный чеклист стола — точечно по багам.

**Критерий:** нельзя спуфить слот, подсмотреть чужие карты, нарисовать себе очки; процесс поднимается на любом Linux по одному runbook.
